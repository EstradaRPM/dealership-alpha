# DealEngine

The "close the deal" core: loan math, credit-tier classification, F&I product attach, front/back gross calculation.

## Public API (`index.ts`)
- `createDealEngine()` → `DealEngine`.
- `classifyCredit`, `loadCreditTiers` — credit-score → tier mapping.
- `computeMonthlyPayment(params, apr)` — pure loan-math helper (PMT-style). Takes the **rate** rather than a tier (#365): the tier table holds the lender's buy rate, and every payment a customer is quoted is built from `buyRate + markup`, so quoting the wrong one has to be a visible choice at the call site. `structure(params: StructureParams)` resolves the customer's rate through `quoteFinance` before calling it.
- `quoteFinance(tier) → FinanceQuote { buyRate, markupPts, customerRate }` (#365) — what the store quotes today. Markup target is `ambientMarkupPts` while no `f&i-manager` is on the desk (grill Q2 — the T1–T2 backend is ambient with no player lever) and the **selected posture's** markup once one is (#366); both are clamped down to the tier's `markupCapPts`, so the subprime program allows the least markup. The input is named (`FinanceQuoteInput { deskStaffed, postureMarkupPts }`) for the #365/#152 reason: a quote resolved against no posture is a silent default. Both halves arrive as closures — `DealEngineDeps.getFniDeskStaffed?: () => boolean` and `getFniPostureMarkupPts?: () => number` — so DealEngine depends on neither StaffOrg nor the save slot, and both are read live so the first F&I hire (or a dial change) moves the next deal. Omitted ⇒ false ⇒ ambient, and ⇒ the catalog's default posture. **Callers hand the SAME quote to the affordability gate and to `closeDeal`**, which is what makes the rate a buyer is qualified at the rate they sign.
- `resolveFniPostureMarkupPts(postureId, config?) → number` (#366) — pure. Resolves a per-slot F&I posture id to its rate markup in points of APR ("More per deal" 2.5 / "Balanced" 1.75 / "More deals" 1.0). Unknown/`undefined` id ⇒ catalog `defaultId`; a retired default ⇒ the first posture — always returns a real markup, which is what lets the composition root hand DealEngine a getter it never null-checks. `loadFniPostureConfig()` reads the `fniPosture` section of `data/tunables.json`. The composition root reads the persisted slot id and threads the result in as `DealEngineDeps.getFniPostureMarkupPts` (live getter, so a mid-game change applies on the next deal). Types `FniPostureOption`, `FniPostureConfig`. **The dial is the player's ONE F&I input and it is standing, not per-deal** (grill Q5/Q9/Q10): no slider, no per-product switch, no manual deal screen, and it is per-**slot** state (grill I7) — nothing about it is in the world snapshot, so there is no envelope bump and no migration to write. "More deals" is a real trade rather than a smaller number: the payment IS built at the marked-up rate, so a thinner markup clears the existing PTI affordability gate for more buyers.
- `computeReserve(input: ReserveInput) → number` (#365) — the store's share of the rate spread, and **honest amortization, not a percentage of amount financed**. The customer's payment is built at `customerRate`; the lender advances the present value of that payment stream discounted at `buyRate`; the dealer keeps `dealerSharePct` of the difference. Falls out of `computeMonthlyPayment` + `computeMaxFinancedAmount`, so it moves correctly with term and principal without a second rate model. Zero without a spread, a principal or a term. `loadFniReserveConfig()` reads the `fniReserve` section of `data/tunables.json`; `resolveFinanceQuote` is the pure form behind `quoteFinance`.
- `fallThroughProbability(markupPts, config?) → number` and `rollFinanceFallThrough(markupPts, seed, config?) → boolean` (#367) — the **contractual** deal-kill, and the teeth that make the F&I posture a decision rather than free money (grill Q3 primary, I8). A contract written past the safe markup frontier doesn't get bought — the lender passes, or the customer rate-shops it and leaves. **One curve, no per-lender branching**: `maxFallThroughRate × clamp01((markupPts − safeFrontierPts) / fullKillRangePts)`, flat past the end of the ramp (a curve that kept climbing would become a wall, not a trade-off). At or under the frontier the answer is exactly **zero**, which is load-bearing: Balanced sits on the frontier and the unstaffed `ambientMarkupPts` sits under it, so no pre-#367 calibration run loses a deal to this — it is the reach past Balanced that costs something. It also means a subprime buyer, whose lender caps markup below the frontier, **cannot be over-marked at all**, so the most desperate customer is not the one you can gouge. The roll is pure + deterministic; the caller derives the seed (`deriveSeed(masterSeed, 'fni.deal_fallthrough', { customerId, day })` at the StaffDispatch flow seam), same split as `rollCustomerCounterResponse`. **Both take an optional trailing `financeStructuringSkill: number | null`** (#369, default `null` = no finance office) which moves the frontier they measure against and nothing else.
- `resolveSafeFrontierPts(financeStructuringSkill, config?) → number` (#369) — the markup this store can write before the lender starts passing, and the one monotonic relation grill Q5 asked for: a better structurer packages the same aggressive rate into paper a lender will actually buy, so the frontier slides out with `finance_structuring` and the peak of the posture dial slides with it. Linear from the bare `safeFrontierPts` at skill 0 to `+ structuringFrontierMaxPts` at `structuringSkillReference`, then **flat** — a manager cannot out-structure the lender forever. The max extension is deliberately the reach from Balanced to "More per deal", so a reference-grade desk can run the aggressive posture with nothing falling through and every desk short of it pays a real fall-through rate. **`null` is "no F&I manager", not "skill 0"** — they coincide numerically today and are still written separately, so a future extension that is nonzero at skill 0 cannot silently grant itself to a store that never hired anyone. Pure, so #370's peak meter reads where this store's frontier sits without closing a deal. **It moves the LENDER's frontier only**: `fniCsiDrag.fairMarkupPts` deliberately does **not** follow it, because a slicker structurer changes what the bank will buy, not how gouged the customer feels — so the aggressive posture never becomes free, it changes which tooth bites. Who the desk is (and therefore the skill) is resolved at the composition root and reaches the roll through StaffDispatch's `getFniDesk`; DealEngine's own `getFniDeskStaffed` still answers the narrower rate question. **This is only the contractual half.** The *structural* kill needed no machinery and is not re-implemented here: the payment is built at the marked-up rate, so an over-marked deal already fails the `ptiCap`/`maxTerm`/`ltvCeiling` gate that has always existed (grill I3). `loadFniDealKillConfig()` reads the `fniDealKill` section of `data/tunables.json`. Type `FniDealKillConfig`.
- `markupSatisfactionHit(markupPts, config?) → number` and `loadFniCsiDragConfig()` (#368) — the **CSI drag**, the second and slower tooth on the posture (grill Q3 secondary). Deal-kill costs the store the deal it was working; this costs it the *next* customer — an over-marked buyer scores the store lower, store satisfaction already feeds `CustomerPool` arrival rates, so gouging thins the crowd. Same curve shape as the kill: `maxSatisfactionHit × clamp01((markupPts − fairMarkupPts) / fullDragRangePts)`, flat past the end, exactly **zero at or under the fair line** — Balanced sits on it and ambient sits under it, so no pre-#368 calibration run takes this hit either. Pure, so #370's peak meter can read the cost of a posture without closing a deal. **The hit is on the MARKUP, never on the products**: attaching a menu is the F&I desk's job, over-marking the rate is the gouge, so a cash deal has no drag at any attach. It rides the **existing** `reputation:satisfaction_hit` channel (Reputation is already its only consumer) rather than opening a second path into the same variable — the producer was added, not a parallel one. `fairMarkupPts` deliberately equals `fniDealKill.safeFrontierPts` so the player learns ONE frontier to read the dial; it is a separate key because the two are separately *measured* (a probability against a satisfaction delta) and because #369 moves the lender's frontier with staff skill — moving the customer's fairness line with it is a design decision, not a calibration nudge. **Chargebacks are a later refinement layer on this same variable** (grill Q3) and are deliberately not here. Type `FniCsiDragConfig`.
- `loadFniProducts` — reads `data/fni-products.json` through `parseData`, per-product `.strict()` (#152) so a mistyped `loanSensitivity` is refused rather than silently stripped into "flat".
- `computeAutoFni(input: AutoFniInput) → AttachedFniProduct[]` — the menu the desk gets signed. Attach = `baseAttachRate × skillMultiplier × loanFactor`, where **`loanFactor = 1 − loanSensitivity × (1 − financedShare)`** and `financedShare = loanAmount / agreedPrice` (0 on cash, #152). One per-product multiplier, no sibling code path. `loanSensitivity` absent ⇒ factor 1, flat across every structure (etch / key / tire & wheel protect the car, not the note). `requiresFinancing` is **categorical and checked ahead of the roll** — GAP covers the gap between a loan balance and the car's value, so it cannot attach to a cash deal at any sensitivity or any RNG value; keeping it a separate key is what stops a calibration pass tuning loan-gap coverage onto a cash sale. The roll is drawn for **every available product whether or not it can attach**, so gating one does not shift the stream for the rest. Input is named rather than positional for the #365 reason: a menu presented against no structure is the silent default this module stopped allowing. The one production caller is StaffDispatch, which resolves the structure *before* presenting.
- `generateTradeAsk(currentVehicle, loanPayoff, bookValueFn, seed, config?)` — pure, deterministic (#167). The customer's trade allowance ask: `book × motivatedSellerMultiplier(seed) + max(0, payoff − book)`. The noise multiplier mirrors the auction-side motivated-seller draw (a clipped Box-Muller normal); the negative-equity term floors an underwater owner's ask toward their payoff. `bookValueFn: TradeBookValueFn` reads honest wholesale book from the trade's `CurrentVehicle` — the live MarketEconomy provider satisfies it (CurrentVehicle carries the anchor fields it reads; the composition root adapts the seam). `loadTradeAllowanceNoiseConfig` reads `data/trade-allowance-noise.json`. Trade machinery accrues here (#168–#172).
- `resolveTradeIn(input, deps) → TradeResolution` — pure, deterministic trade auto-resolution (#169) + manager-attention escalation (#170). Composes `evaluateTrade` with the routine gate, the negative-equity guard, and the escalation/approver model. A trade is *routine* (status `resolved`, `approver: 'auto'`) when the salesperson's evaluation didn't decline, `ask − target ≤ target × routineGapFraction`, condition-read confidence ≥ `routineConfidenceFloor`, **and** the lien overhang `payoff − target ≤ target × negativeEquityEscalationMargin`; routine accepts agree at the ask, routine counters agree at the staff counter (`hadCounter`). `tradeEquity = agreedAllowance − payoff` (≥ 0). Routine-but-underwater (`allowance < payoff`, small overhang) → `abandoned` (`reason: 'negative_equity'`). Anything else is *unusual* and escalates: with a `TradeApprover` (GM/UCM) on staff and the ask under the player override, the manager re-decides via `evaluateTrade` with the **extended** counter window (`managerCounterWindowFraction`) + their own NEGOTIATE skill → `resolved` (with the manager's `approver` tag) or `abandoned`/`manager_declined`; otherwise (no manager, or ask over `playerOverrideThreshold`) → status `player_review` carrying `TradeReviewPayload` (book/ask/payoff/target/recommendedCounter/staffConfidence) for the #84 overlay. Reads `target` off `evaluateTrade` (no formula re-derivation). Types `TradeResolution`, `TradeResolutionInput`, `TradeResolutionDeps`, `TradeApprover`, `TradeReviewPayload`.
- `isTradeApprovalUnlocked(ucmConditionReadingSkill, threshold) → boolean` — pure channel-desk trade auto-approval gate (#291/M4). `skill !== null && skill ≥ threshold`; `null` = no UCM ⇒ locked. Sibling to `isAutoPricingUnlocked` (M2) / `isDiscountDeskingUnlocked` (M3) — the advise/act split: the appraisal *advice* (`getTradeConditionRead`/#163) is free on hire, auto-approving FOR the player is earned.
- `resolveTradeApprover(candidates, conditionReadingThreshold) → TradeApprover | null` — pure (#291/M4). Resolves the escalation approver with **GM > gated-UCM > player** priority. The GM trumps the gate (never gated); a UCM approves only once the *top* UCM `condition_reading` clears the threshold (via `isTradeApprovalUnlocked`), else `null` ⇒ escalate to the player. Returns the best-NEGOTIATE candidate of the winning pool (extended-counter skill). The composition root maps its live StaffOrg roster down to the narrow `ApproverCandidate` (`{ role, conditionReading, skill }`) so DealEngine never depends on StaffOrg, and feeds it as `getTradeApprover`. Type `ApproverCandidate`.
- `rollCustomerCounterResponse(input, seed, config?) → boolean` — pure, deterministic customer accept/reject on a PLAYER counter (#170). `acceptProb = clamp01(1 − gapFraction · counterGapAversion · (1 + priceSensitivity · counterSensitivityWeight))` where `gapFraction = (ask − counter)/ask`; a counter ≥ ask accepts outright. Caller derives the seed (`deriveSeed(masterSeed, 'trade_counter_response', { customerId, day })`). Type `CustomerCounterInput`.
- `evaluateTrade(input, deps) → TradeEvaluation { action: 'accept'|'counter'|'decline', counterAmount?, target, rationale }` — pure, deterministic staff decision engine (#168). `target` (the internal acceptance target, #169) is exposed so `resolveTradeIn` reads it instead of re-deriving the formula. Reads `bookValueFn`, the salesperson's resolved NEGOTIATE composite (`NegotiationSkill`, mirrors SalesProcess `GateSkill` — defined locally to avoid a SalesProcess→DealEngine cycle), and a UCM `TradeConditionRead | null` (mirrors StaffOrg `ConditionRead`; only `confidence` is read, `null` = no UCM = most generous = the margin floor). Channel-desk margin (#291/M4): `target = book × policyMultiplier × (1 + (1−confidence)·appraisalGenerosityPremium + driftLoosening)` — a green/absent appraiser pads the allowance ABOVE book (generous → thin margin); a sharp UCM tightens it down toward book (better margin). **Monotonic in `condition_reading`; no UCM (confidence 0) = the most generous target = the margin floor.** Channel-desk M5 (#292): the optional `allowanceDrift` (`TradeAllowanceDrift = { conditionReadingSkill, seed, config }`) adds a skill-scaled, seeded `driftLoosening = NPC.skillDriftFraction(...)` ON TOP of the M4 baseline (unified — both key on `condition_reading` and both loosen toward worse). A green-but-gated UCM lets the target drift looser still; a UCM at/above `skillReference` holds at the M4 baseline (zero drift). Threaded through both the salesperson and manager `evaluateTrade` passes by `resolveTradeIn` (it's an appraisal property, not a negotiator one). Omit ⇒ no drift. The composition root seeds it per-(customer, day) ⇒ replay-safe. `config` = `managerGates.executionDrift.condition_reading`. ask ≤ target → accept; within `counterWindowFraction` above → counter; far above → counter only if NEGOTIATE effectiveness ≥ `skillCounterThreshold`, else decline. `counterAmount = target + (ask−target)·(1−effectiveness)·counterGiveWeight` — low NEGOTIATE skill over-pays (drifts toward the ask). `policyMultiplier` is the slice-#18 trade-policy seam (default `1.0` = market). `loadTradeEvalConfig` reads `data/trade-evaluation.json`. No flow integration this slice.
- `resolveTradePolicyMultiplier(policyId, config?) → number` — pure (#172). Resolves a per-slot trade-policy id to its acceptance-target multiplier (`aggressive` 1.1 / `market` 1.0 / `conservative` 0.92). Unknown/`undefined` id ⇒ catalog `defaultId`; missing default ⇒ first policy — always returns a real multiplier. The composition root reads the persisted slot id and threads the result into `resolveTradeIn`'s `policyMultiplier` (live getter, so a Settings change applies on the next trade). `loadTradePolicyConfig()` reads the `tradePolicy` section of `data/tunables.json`. Default `market` = 1.0 leaves the #94 calibration path untouched. Types `TradePolicyOption`, `TradePolicyConfig`.
- Types: `DealEngine`, `DealEngineDeps`, `CreditTier`, `CreditTierCatalog`, `TierDef`, `LoanParams`, `LoanResult`, `CloseDealParams`, `ClosedDealResult`, `FniProduct`, `FniProductCatalog`, `AttachedFniProduct`, `AutoFniDeal`, `AutoFniInput`, `TradeAllowanceNoiseConfig`, `TradeBookValueFn`, `TradeEvalConfig`, `TradeEvaluation`, `TradeEvalInput`, `TradeEvalDeps`, `TradeAction`, `NegotiationSkill`, `TradeConditionRead`, `TradeApprover`, `ApproverCandidate`, `TradePolicyOption`, `TradePolicyConfig`.

## Events
- **Emits:** `deal:closed` (with `agreedPrice`, `frontGross`, `backGross` — now the SUM of `productGross` (margin on what attached) and `reserveGross` (the rate spread, 0 on cash), both carried on the payload and on `ClosedDealResult` so a reader can name which half moved, #365; `apr` on both is the CUSTOMER's rate, and `CloseDealParams.buyRate` is the lender's cost of money behind it — omitted ⇒ equals `apr` ⇒ no spread ⇒ no reserve, the behavior-neutral default for pre-#365 harnesses. Reserve **posts revenue** (`F&I: finance reserve`) like every other income line — reporting it as gross without banking it would leave the Finance tab's breakdown unable to reconcile with its own net income; it is recognized at the close rather than at lender funding because the receivable lag is not modeled anywhere here, and — when the caller ran a sales process — the `salesQuality` trio it round-trips from `CloseDealParams`, #363; DealEngine never reads it, `CustomerPool` publishes it onto `customer:resolved`). `regulatory:lemon_law_incident` (un-reconditioned `major`/`catastrophic` lemon retailed — IndictmentMonitor producer). `deal:fraud_flag` (#327 — payment packing: a *financed* deal whose F&I retail burden `Σ price` exceeds `packFraction × agreedPrice` is a structuring/disclosure violation; IndictmentMonitor producer; gate is financed-only since a cash sale can't pack a payment). `reputation:satisfaction_hit` with `reason: 'fni_rate_markup'` (#368 — the CSI drag on a financed close written past `fniCsiDrag.fairMarkupPts`, scaled by the excess; the existing channel, not a new one). `trade:resolved` (#169) and `trade:escalated` (#170) are published by the close-flow caller (StaffDispatch), not DealEngine itself — `resolveTradeIn` is a pure function, so the emits live at the flow seam. `trade:escalated` carries the full `TradeReviewPayload` so the #84 overlay needs no further lookups.
- **Triggers downstream:** `Inventory` removes the vehicle, `Economy` posts revenue, `Reputation` may adjust based on terms.

## Data
- `data/credit-tiers.json` — tier breakpoints, the lender's `buyRate`, and `markupCapPts` per tier. **`apr` is gone** (#365) — it named the customer's rate while holding the wholesale one. `TierDefSchema` is `.strict()` so a stale `apr` key is refused rather than silently stripped. Deliberately **no lender flats**: a flat is a second pricing rule the player can neither see nor move (grill I2).
- `data/tunables.json` § `fniReserve` — `dealerSharePct`, `ambientMarkupPts`. The DESKED target is not here: it is whichever `fniPosture` the player selected (#366 deleted `balancedMarkupPts`, which held the same number in a second place). Placeholder magnitudes owed to a #286-class calibration pass (grill I9).
- `data/tunables.json` § `fniDealKill` — the one contractual deal-kill curve (`safeFrontierPts`, `fullKillRangePts`, `maxFallThroughRate`, #367) plus the frontier's skill extension (`structuringFrontierMaxPts`, `structuringSkillReference`, #369), in the same points-of-APR unit as `fniPosture.markupPts` and `markupCapPts`. Placeholder magnitudes owed to a #286-class pass (grill I9).
- `data/tunables.json` § `fniCsiDrag` — the CSI-drag curve (`fairMarkupPts`, `fullDragRangePts`, `maxSatisfactionHit`, #368), same points-of-APR unit as `fniDealKill`. The schema **refuses a non-negative `maxSatisfactionHit`** — a positive number would mean gouging cheers the store up, and would read as balance rather than as a dropped minus sign. Placeholder magnitudes owed to a #286-class pass (grill I9).
- `data/tunables.json` § `fniPosture` — the three-position posture catalog (`defaultId` + `postures[]` with `id`/`label`/`markupPts`/`blurb`), same shape as `tradePolicy`. Player-facing copy lives here, so the dial retunes and rewords without touching code.
- `data/fni-products.json` — product catalog, costs, and per-product `loanSensitivity` / `requiresFinancing` (#152). Magnitudes are placeholders owed to a #286-class pass (grill I9).
- `data/deal-fraud.json` — payment-packing threshold (`packFraction`, #327), loaded by `loadDealFraudConfig`.

## Realism note
This module follows real F&I conventions (front gross, back gross, reserve, etc.). Don't shortcut the math — the user has deep domain expertise and will catch fudges.
