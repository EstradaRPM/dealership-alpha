# DealEngine

The "close the deal" core: loan math, credit-tier classification, F&I product attach, front/back gross calculation.

## Public API (`index.ts`)
- `createDealEngine()` → `DealEngine`.
- `classifyCredit`, `loadCreditTiers` — credit-score → tier mapping.
- `computeMonthlyPayment(params, apr)` — pure loan-math helper (PMT-style). Takes the **rate** rather than a tier (#365): the tier table holds the lender's buy rate, and every payment a customer is quoted is built from `buyRate + markup`, so quoting the wrong one has to be a visible choice at the call site. `structure(params: StructureParams)` resolves the customer's rate through `quoteFinance` before calling it.
- `quoteFinance(tier) → FinanceQuote { buyRate, markupPts, customerRate }` (#365) — what the store quotes today. Markup target is `ambientMarkupPts` while no `f&i-manager` is on the desk (grill Q2 — the T1–T2 backend is ambient with no player lever) and `balancedMarkupPts` once one is (#366 turns that into the three-position posture dial); both are clamped down to the tier's `markupCapPts`, so the subprime program allows the least markup. The desk read arrives as `DealEngineDeps.getFniDeskStaffed?: () => boolean` — a closure, so DealEngine never depends on StaffOrg, read live so the first F&I hire moves the next deal. Omitted ⇒ false ⇒ ambient. **Callers hand the SAME quote to the affordability gate and to `closeDeal`**, which is what makes the rate a buyer is qualified at the rate they sign.
- `computeReserve(input: ReserveInput) → number` (#365) — the store's share of the rate spread, and **honest amortization, not a percentage of amount financed**. The customer's payment is built at `customerRate`; the lender advances the present value of that payment stream discounted at `buyRate`; the dealer keeps `dealerSharePct` of the difference. Falls out of `computeMonthlyPayment` + `computeMaxFinancedAmount`, so it moves correctly with term and principal without a second rate model. Zero without a spread, a principal or a term. `loadFniReserveConfig()` reads the `fniReserve` section of `data/tunables.json`; `resolveFinanceQuote` is the pure form behind `quoteFinance`.
- `loadFniProducts` — reads `data/fni-products.json`.
- `generateTradeAsk(currentVehicle, loanPayoff, bookValueFn, seed, config?)` — pure, deterministic (#167). The customer's trade allowance ask: `book × motivatedSellerMultiplier(seed) + max(0, payoff − book)`. The noise multiplier mirrors the auction-side motivated-seller draw (a clipped Box-Muller normal); the negative-equity term floors an underwater owner's ask toward their payoff. `bookValueFn: TradeBookValueFn` reads honest wholesale book from the trade's `CurrentVehicle` — the live MarketEconomy provider satisfies it (CurrentVehicle carries the anchor fields it reads; the composition root adapts the seam). `loadTradeAllowanceNoiseConfig` reads `data/trade-allowance-noise.json`. Trade machinery accrues here (#168–#172).
- `resolveTradeIn(input, deps) → TradeResolution` — pure, deterministic trade auto-resolution (#169) + manager-attention escalation (#170). Composes `evaluateTrade` with the routine gate, the negative-equity guard, and the escalation/approver model. A trade is *routine* (status `resolved`, `approver: 'auto'`) when the salesperson's evaluation didn't decline, `ask − target ≤ target × routineGapFraction`, condition-read confidence ≥ `routineConfidenceFloor`, **and** the lien overhang `payoff − target ≤ target × negativeEquityEscalationMargin`; routine accepts agree at the ask, routine counters agree at the staff counter (`hadCounter`). `tradeEquity = agreedAllowance − payoff` (≥ 0). Routine-but-underwater (`allowance < payoff`, small overhang) → `abandoned` (`reason: 'negative_equity'`). Anything else is *unusual* and escalates: with a `TradeApprover` (GM/UCM) on staff and the ask under the player override, the manager re-decides via `evaluateTrade` with the **extended** counter window (`managerCounterWindowFraction`) + their own NEGOTIATE skill → `resolved` (with the manager's `approver` tag) or `abandoned`/`manager_declined`; otherwise (no manager, or ask over `playerOverrideThreshold`) → status `player_review` carrying `TradeReviewPayload` (book/ask/payoff/target/recommendedCounter/staffConfidence) for the #84 overlay. Reads `target` off `evaluateTrade` (no formula re-derivation). Types `TradeResolution`, `TradeResolutionInput`, `TradeResolutionDeps`, `TradeApprover`, `TradeReviewPayload`.
- `isTradeApprovalUnlocked(ucmConditionReadingSkill, threshold) → boolean` — pure channel-desk trade auto-approval gate (#291/M4). `skill !== null && skill ≥ threshold`; `null` = no UCM ⇒ locked. Sibling to `isAutoPricingUnlocked` (M2) / `isDiscountDeskingUnlocked` (M3) — the advise/act split: the appraisal *advice* (`getTradeConditionRead`/#163) is free on hire, auto-approving FOR the player is earned.
- `resolveTradeApprover(candidates, conditionReadingThreshold) → TradeApprover | null` — pure (#291/M4). Resolves the escalation approver with **GM > gated-UCM > player** priority. The GM trumps the gate (never gated); a UCM approves only once the *top* UCM `condition_reading` clears the threshold (via `isTradeApprovalUnlocked`), else `null` ⇒ escalate to the player. Returns the best-NEGOTIATE candidate of the winning pool (extended-counter skill). The composition root maps its live StaffOrg roster down to the narrow `ApproverCandidate` (`{ role, conditionReading, skill }`) so DealEngine never depends on StaffOrg, and feeds it as `getTradeApprover`. Type `ApproverCandidate`.
- `rollCustomerCounterResponse(input, seed, config?) → boolean` — pure, deterministic customer accept/reject on a PLAYER counter (#170). `acceptProb = clamp01(1 − gapFraction · counterGapAversion · (1 + priceSensitivity · counterSensitivityWeight))` where `gapFraction = (ask − counter)/ask`; a counter ≥ ask accepts outright. Caller derives the seed (`deriveSeed(masterSeed, 'trade_counter_response', { customerId, day })`). Type `CustomerCounterInput`.
- `evaluateTrade(input, deps) → TradeEvaluation { action: 'accept'|'counter'|'decline', counterAmount?, target, rationale }` — pure, deterministic staff decision engine (#168). `target` (the internal acceptance target, #169) is exposed so `resolveTradeIn` reads it instead of re-deriving the formula. Reads `bookValueFn`, the salesperson's resolved NEGOTIATE composite (`NegotiationSkill`, mirrors SalesProcess `GateSkill` — defined locally to avoid a SalesProcess→DealEngine cycle), and a UCM `TradeConditionRead | null` (mirrors StaffOrg `ConditionRead`; only `confidence` is read, `null` = no UCM = most generous = the margin floor). Channel-desk margin (#291/M4): `target = book × policyMultiplier × (1 + (1−confidence)·appraisalGenerosityPremium + driftLoosening)` — a green/absent appraiser pads the allowance ABOVE book (generous → thin margin); a sharp UCM tightens it down toward book (better margin). **Monotonic in `condition_reading`; no UCM (confidence 0) = the most generous target = the margin floor.** Channel-desk M5 (#292): the optional `allowanceDrift` (`TradeAllowanceDrift = { conditionReadingSkill, seed, config }`) adds a skill-scaled, seeded `driftLoosening = NPC.skillDriftFraction(...)` ON TOP of the M4 baseline (unified — both key on `condition_reading` and both loosen toward worse). A green-but-gated UCM lets the target drift looser still; a UCM at/above `skillReference` holds at the M4 baseline (zero drift). Threaded through both the salesperson and manager `evaluateTrade` passes by `resolveTradeIn` (it's an appraisal property, not a negotiator one). Omit ⇒ no drift. The composition root seeds it per-(customer, day) ⇒ replay-safe. `config` = `managerGates.executionDrift.condition_reading`. ask ≤ target → accept; within `counterWindowFraction` above → counter; far above → counter only if NEGOTIATE effectiveness ≥ `skillCounterThreshold`, else decline. `counterAmount = target + (ask−target)·(1−effectiveness)·counterGiveWeight` — low NEGOTIATE skill over-pays (drifts toward the ask). `policyMultiplier` is the slice-#18 trade-policy seam (default `1.0` = market). `loadTradeEvalConfig` reads `data/trade-evaluation.json`. No flow integration this slice.
- `resolveTradePolicyMultiplier(policyId, config?) → number` — pure (#172). Resolves a per-slot trade-policy id to its acceptance-target multiplier (`aggressive` 1.1 / `market` 1.0 / `conservative` 0.92). Unknown/`undefined` id ⇒ catalog `defaultId`; missing default ⇒ first policy — always returns a real multiplier. The composition root reads the persisted slot id and threads the result into `resolveTradeIn`'s `policyMultiplier` (live getter, so a Settings change applies on the next trade). `loadTradePolicyConfig()` reads the `tradePolicy` section of `data/tunables.json`. Default `market` = 1.0 leaves the #94 calibration path untouched. Types `TradePolicyOption`, `TradePolicyConfig`.
- Types: `DealEngine`, `DealEngineDeps`, `CreditTier`, `CreditTierCatalog`, `TierDef`, `LoanParams`, `LoanResult`, `CloseDealParams`, `ClosedDealResult`, `FniProduct`, `FniProductCatalog`, `AttachedFniProduct`, `TradeAllowanceNoiseConfig`, `TradeBookValueFn`, `TradeEvalConfig`, `TradeEvaluation`, `TradeEvalInput`, `TradeEvalDeps`, `TradeAction`, `NegotiationSkill`, `TradeConditionRead`, `TradeApprover`, `ApproverCandidate`, `TradePolicyOption`, `TradePolicyConfig`.

## Events
- **Emits:** `deal:closed` (with `agreedPrice`, `frontGross`, `backGross` — now the SUM of `productGross` (margin on what attached) and `reserveGross` (the rate spread, 0 on cash), both carried on the payload and on `ClosedDealResult` so a reader can name which half moved, #365; `apr` on both is the CUSTOMER's rate, and `CloseDealParams.buyRate` is the lender's cost of money behind it — omitted ⇒ equals `apr` ⇒ no spread ⇒ no reserve, the behavior-neutral default for pre-#365 harnesses. Reserve **posts revenue** (`F&I: finance reserve`) like every other income line — reporting it as gross without banking it would leave the Finance tab's breakdown unable to reconcile with its own net income; it is recognized at the close rather than at lender funding because the receivable lag is not modeled anywhere here, and — when the caller ran a sales process — the `salesQuality` trio it round-trips from `CloseDealParams`, #363; DealEngine never reads it, `CustomerPool` publishes it onto `customer:resolved`). `regulatory:lemon_law_incident` (un-reconditioned `major`/`catastrophic` lemon retailed — IndictmentMonitor producer). `deal:fraud_flag` (#327 — payment packing: a *financed* deal whose F&I retail burden `Σ price` exceeds `packFraction × agreedPrice` is a structuring/disclosure violation; IndictmentMonitor producer; gate is financed-only since a cash sale can't pack a payment). `trade:resolved` (#169) and `trade:escalated` (#170) are published by the close-flow caller (StaffDispatch), not DealEngine itself — `resolveTradeIn` is a pure function, so the emits live at the flow seam. `trade:escalated` carries the full `TradeReviewPayload` so the #84 overlay needs no further lookups.
- **Triggers downstream:** `Inventory` removes the vehicle, `Economy` posts revenue, `Reputation` may adjust based on terms.

## Data
- `data/credit-tiers.json` — tier breakpoints, the lender's `buyRate`, and `markupCapPts` per tier. **`apr` is gone** (#365) — it named the customer's rate while holding the wholesale one. `TierDefSchema` is `.strict()` so a stale `apr` key is refused rather than silently stripped. Deliberately **no lender flats**: a flat is a second pricing rule the player can neither see nor move (grill I2).
- `data/tunables.json` § `fniReserve` — `dealerSharePct`, `ambientMarkupPts`, `balancedMarkupPts`. Placeholder magnitudes owed to a #286-class calibration pass (grill I9).
- `data/fni-products.json` — product catalog, costs, presentation flow.
- `data/deal-fraud.json` — payment-packing threshold (`packFraction`, #327), loaded by `loadDealFraudConfig`.

## Realism note
This module follows real F&I conventions (front gross, back gross, reserve, etc.). Don't shortcut the math — the user has deep domain expertise and will catch fudges.
